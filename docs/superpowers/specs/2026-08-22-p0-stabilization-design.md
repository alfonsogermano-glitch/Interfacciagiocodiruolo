# Hollowgate — P0 Stabilization Design

Date: 2026-08-22
Branch: `stabilization/p0`

## Objective

Stabilize the current production architecture before resuming feature development. The P0 work must reduce regression risk without changing product behavior unnecessarily, preserve existing campaign/user data, and leave the project with a repeatable verification path for future changes.

## Scope

P0 is split into four ordered stages. Each stage must be independently verifiable and must not rely on a later stage to be safe.

### P0.1 — Code guardrails

Introduce a real TypeScript type-check without changing the runtime build model.

Planned changes:

- add TypeScript as a pinned development dependency and keep npm/package-lock as the package manager source of truth;
- add a minimal `tsconfig.json` suitable for the existing Vite + React codebase;
- keep `strict` disabled initially so the legacy codebase is not forced through a broad unrelated refactor;
- add `typecheck` (`tsc --noEmit`) and `check` scripts;
- make `check` run the production build plus the type-check;
- fix the small set of currently known type errors rather than suppressing them globally;
- add a minimal GitHub Actions workflow using `npm ci` and `npm run check` on pushes/PRs;
- do not change user-visible behavior in this stage.

Success criteria:

- `npm ci` succeeds from the committed lockfile;
- `npm run build` succeeds;
- `npm run typecheck` succeeds;
- GitHub Actions executes the same checks on the branch.

### P0.2 — Supabase schema and Storage security

Bring the live schema in line with already-shipped frontend behavior and remove obsolete permissive Storage policies.

Planned schema change:

- add nullable `characters.adventure_id` referencing `adventures(id)` with appropriate index;
- preserve all existing character rows;
- verify that current character save/load paths persist the field after the change.

Planned Storage security change:

- keep public read access where Hollowgate currently depends on public asset URLs;
- keep authenticated upload/update/delete policies restricted to the authenticated user's own storage folder where that is the intended ownership model;
- remove only obsolete broader policies that currently allow an authenticated user to modify arbitrary objects in `character-portraits` or `npc-images`;
- do not delete or move stored files.

Verification:

- inspect final policies after changes;
- verify allowed owner operations and blocked cross-user writes;
- run Supabase security/performance advisors after schema/policy changes;
- verify application image rendering still works.

### P0.3 — Canonical campaign source of truth

Make PostgreSQL the canonical data store for campaign and membership existence. The autogenerated Figma Make KV store must stop being a competing source of truth.

Current constraint:

- campaign data is split between KV keys and `public.campaigns` / `public.campaign_members`;
- some rows exist only in KV and some only in SQL;
- some SQL-only campaigns still have related NPC/monster/adventure data, so destructive cleanup is forbidden during migration.

Migration approach:

1. inventory KV and SQL campaign/member sets immediately before migration;
2. backfill SQL with campaigns and memberships that exist only in KV, preserving IDs and ownership;
3. leave SQL-only campaigns intact pending explicit classification, because related entity data exists;
4. update Edge Function campaign/member reads and writes to use PostgreSQL as canonical storage;
5. retain temporary compatibility mirroring to KV only where needed during rollout;
6. validate create/join/leave/remove/session/member flows against PostgreSQL;
7. remove compatibility KV writes only after live verification;
8. migrate invite-code persistence away from `inviteCode:*` KV keys into a structured SQL representation as part of the same source-of-truth consolidation, with uniqueness and expiry/validity behavior matching current product semantics.

No campaign, member, character, NPC, monster, adventure or note may be deleted automatically as part of this stage.

### P0.4 — End-to-end verification and closure

Before P0 is considered complete, verify at minimum:

- login/session bootstrap;
- campaign creation;
- campaign selection and reload;
- invite preview and join;
- player leave/removal;
- member list and ownership display;
- session activation/deactivation;
- character, NPC and monster visibility/load;
- folders;
- campaign realtime updates;
- note/realtime basics;
- production build and type-check;
- Supabase advisors.

## Data safety rules

- Never delete legacy campaign or membership data solely because it appears stale.
- Take before/after aggregate counts for every data migration.
- Prefer additive/backfill changes before destructive cleanup.
- Migration SQL must be idempotent where practical.
- A failed write must surface as an error; local fallback must not be treated as proof that the cloud write succeeded.
- Service-role credentials remain server-side only.

## Branch and deployment strategy

- All P0 work is performed on `stabilization/p0` or narrower child branches if a stage becomes large.
- `main` remains production.
- Each P0 stage should form a reviewable changeset.
- Database/Edge Function deployment order must be explicitly documented in the corresponding commit/PR when client compatibility depends on it.
- No direct destructive production database operation is performed without a pre-change verification query and an immediate post-change verification query.

## Rollback strategy

P0.1 can be rolled back by reverting the branch commit because it is tooling-only.

P0.2 schema addition is backward-compatible because `characters.adventure_id` is nullable. Storage-policy rollback consists of restoring the previous policy definitions; object data is not changed.

P0.3 rollout is deliberately transitional: PostgreSQL becomes canonical before KV compatibility is removed. If a server regression is detected during this window, the Edge Function can be reverted while the backfilled SQL rows remain harmless and preserved.

## Non-goals

The following are intentionally not part of P0:

- Map implementation;
- Combat/Encounter/Phases cloud persistence;
- character inventory migration to `character_equipment`;
- requestable NPC implementation;
- global online presence;
- full CoC/D20 character-sheet support;
- broad UI refactors;
- removal of all local/Tauri storage paths;
- modularization of the full Edge Function;
- cleanup of every legacy file.

Those items resume only after the P0 base is verified.

## Definition of done

P0 is complete when the project has a repeatable automated code check, the known critical Supabase schema/security drift is corrected, campaign/membership existence has one canonical PostgreSQL source of truth, and the core multi-user campaign flows pass end-to-end verification without data loss.
